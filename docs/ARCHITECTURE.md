# Архитектура и границы

`cmd/lanprint` — вход, локальная конфигурация и ротация логов. `internal/gui` — нативный Win32 UI без сторонних компонентов. `internal/platform` — Windows API (GDI, Print Spooler) и PowerShell 5.1 для перечисления/явно подтверждаемой сетевой настройки. `internal/core` — конфигурация, ACL, ограниченная очередь, RAW TCP, IPP, mDNS и HTTP.

Все входные задания проверяются до постановки в очередь: ограничение байтов, MIME и UTF-8, размеры изображений до 20 MP. Очередь обрабатывается одним worker. Лимиты по умолчанию: 32 MiB/задание, 32 pending jobs, 8 одновременно открытых TCP connections на все сервисы, 30 секунд на загрузку печатного задания. Очередь и текущие сетевые uploads могут потреблять значительную память в пределах этих лимитов: настройте их под ПК. Последние 256 метаданных заданий сохраняются в памяти, логи ротируются. Документы не копируются во временные файлы.

Текст выводится постранично GDI TextOutW фиксированным шрифтом, изображения — StretchDIBits с масштабированием в printable area. Используется драйвер выбранного принтера: GDI/Spooler формируют его native данные. RAW passthrough вызывает StartDocPrinter/WritePrinter с типом RAW и не выполняет конвертацию. Драйвер может зависнуть внутри системного API; timeout для аппаратно зависшего драйвера не гарантируется.

IPP реализует отдельные операции, не полную спецификацию. Create-Job/Send-Document, multi-document, copies >1, compression, full media/job-template negotiation не поддерживаются. Дополнительные неизвестные job-template attributes не применяются. Validate-Job проверяет доступный MIME/копии/компрессию; реальная проверка содержимого выполняется Print-Job. Не объявляется AirPrint/Mopria/IPP Everywhere.

`pending`, `processing`, `spooled`, `aborted`, `canceled` — состояния LANPrint. `spooled` не объявляется физическим completed: IPP сообщает processing/job-queued-for-marker, а окно позволяет запросить реальную Windows queue. Полный сквозной мониторинг завершения и сохраняемая очередь не реализованы. Job ID относится к текущему запуску queue; после перезапуска повторно начинается с 1. Клиенты должны заново получить job-uri/ID после restart.

mDNS содержит PTR/SRV/TXT/A записи, использует интерфейсный IPv4, порт 5353 и TTL255. Объявления имеют TTL120, повторяются раз в 60s и удаляются goodbye при остановке. Это минимальный responder: конфликт имён/probing, полный cache/QU negotiation не реализованы, поэтому выбирайте уникальное имя и проверяйте обнаружение реальными клиентами. Discovery failure логируется, TCP службы остаются доступны.

HTTP admin read/cancel требует случайный 256-битный Bearer token; сам login shell доступен из разрешённой подсети без раскрытия конфигурации. IPP/RAW печать ограничены ACL, но не аутентифицированы: разрешённые LAN клиенты могут печатать. IPP отмена требует admin token; GUI использует локальные права. HTTP без TLS — только доверенная LAN, без WAN forwarding. CORS не разрешён; токен не хранится в браузере и не передаётся query-параметром. Metadata IPP queries доступны разрешённым клиентам.

Управление сетью: EXE включает канонический `internal/platform/bridge.ps1` через `go:embed`. GUI предлагает физический Ethernet только как uplink, а в списке endpoints оставляет только выделенный виртуальный адаптер с `HardwareInterface=false`. После диалога согласия и UAC ShellExecuteEx запускает embedded script, приложение ждёт process handle и разбирает JSON результат в локальном временном файле; файл удаляется после чтения. Параметры передаются JSON/Base64, без интерполяции пользовательских строк как кода PowerShell.

Помощник проверяет Windows edition/Hyper-V, при необходимости включает optional feature без automatic reboot, создаёт либо повторно использует соответствующий External Switch и отдельную ManagementOS NIC LANPrint-Printer. Ошибки несовместимого существующего switch/NIC обнаруживаются до переподключения; существующий статический адрес виртуального адаптера не сбрасывается. Новый адаптер использует DHCP; Windows выполняет DHCP/DAD. App принимает только Preferred IPv4 без APIPA и не переводит службы на основной IP при отсутствии аренды.

Shared режим удалён. Windows runtime validation запрещает любые endpoints кроме `vEthernet (LANPrint-Printer)`, включая headless mode. DHCP/Static API также отказывает для физического адаптера. Загрузка старой конфигурации сохраняет принтер/токен, но очищает host IP и переключает endpoint на выделенный виртуальный адаптер без сетевых изменений. Linux тесты core используют loopback с fake backend для функциональной проверки протоколов; это тестовая машина, а не поддерживаемый Linux runtime принтера.

При появлении/смене DHCP IP GUI останавливает свои listeners и восстанавливает их на виртуальном адресе. Неполученный IP остаётся состоянием ожидания, а не поводом подключиться к физической NIC. Firewall address rules требуют отдельного обновления. External Switch кратковременно влияет на host uplink при создании: интерфейс LANPrint отдельный, но он остаётся в сетевом стеке ManagementOS Windows. Аппаратная приёмка отдельной MAC/IP и физической печати не может быть заменена кросс-сборкой.

VLAN применяется только к порту LANPrint-Printer: Hyper-V Access VLAN 1–4094 либо Untagged при ID0. External uplink принимает/отправляет IEEE802.1Q кадры, switch выполняет фильтрацию и снятие/добавление тега, а ManagementOS NIC получает обычные кадры своей VLAN. Не создаётся vendor-specific физический VLAN subinterface; VLAN-aware bridge является механизмом Windows для этой схемы. Основной host management adapter и другие VM ports не перенастраиваются. При VLAN change виртуальный DHCP lease очищается/запрашивается заново; Static IP сохраняется с предупреждением. Указанная VLAN входит в saved config и authenticated HTTP status; внешний коммутатор/роутер должны разрешать её и предоставлять DHCP/subnet.
